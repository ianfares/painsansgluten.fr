## 2026-10-05 — T00 — Base de données

- **MariaDB** utilisée aussi bien en développement qu'en test (pas de SQLite, même en test) : le projet repose sur des verrous transactionnels (`lockForUpdate`) et une numérotation séquentielle critique (factures, commandes) dont le comportement diffère entre moteurs SQL. Tester sur un moteur différent de la production aurait pu masquer de vrais bugs de concurrence. Alternative écartée : SQLite en mémoire (défaut Laravel), plus rapide mais jugé risqué ici.
- Deux bases locales créées manuellement (accès root MariaDB non disponible depuis les outils automatisés — nécessite un geste humain avec mot de passe) : `boulangerie_gluten` (dev) et `boulangerie_gluten_test` (tests), toutes deux accessibles par un utilisateur MariaDB dédié `boulangerie_gluten` (pas de compte `root` utilisé par l'application : moindre privilège).
- `phpunit.xml` ne surcharge que `DB_CONNECTION` et `DB_DATABASE` pour les tests ; hôte/identifiants restent lus depuis `.env` (jamais commités) pour ne jamais exposer de secret dans un fichier versionné.

## 2026-10-05 — T02 — Modèle de données

- **Table `users`** : la migration par défaut de Laravel (`name`) a été adaptée dans une **nouvelle** migration (`adjust_users_table_for_v1`) plutôt que modifiée directement, conformément à CLAUDE.md §3.4 (une migration déjà mergée dans `develop` ne se modifie jamais). Résultat : `first_name`/`last_name` séparés (PLAN.md §22), `phone` (obligatoire pour le SMS Chronopost, PLAN §9.1), `deletion_requested_at` (PLAN §13).
- **`orders.relay_snapshot`** stocké en JSON plutôt qu'en colonnes séparées (`relay_address_*`) : PLAN.md §9.4 identifie explicitement cette zone comme ambiguë ("quels champs exacts pour le snapshot complet ?"). Le JSON permet de capturer tout ce que l'API Chronopost renvoie (nom, adresse, horaires, distance) sans décider prématurément d'un schéma rigide ; `relay_id` et `relay_name` restent des colonnes dédiées (recherche/affichage rapides).
- **Pas de table `vat_rates`** : le modèle de données `PLAN.md §22` ne prévoit pas de table séparée pour les taux de TVA, seulement une colonne `products.vat_rate` (decimal). La "liste paramétrable" des taux sélectionnables en BO (mentionnée dans la fiche T02) relève de `spatie/laravel-settings`, installé en **T04** — non disponible en T02. Reporté à T04 : seeding réel des taux à ce moment-là (valeurs toujours **À CONFIRMER** par le comptable, CLAUDE.md §3.1).
- **Redirection générique `/products/{slug}` → `/produit/{slug}`** (PLAN §23) : non seedée dans `redirects` (table de correspondances exactes). C'est une règle de motif, implémentée dans le middleware de redirection (**T20**), pas une ligne de données.
- **`order_status_histories`** : table d'audit append-only, `UPDATED_AT` désactivé (`const UPDATED_AT = null`) — une ligne d'historique ne se modifie jamais.
- Les transitions de statut autorisées (PLAN §9.2) sont encodées directement sur l'enum `OrderStatus::allowedNextStatuses()` (donnée statique), pas dans un service séparé : `App\Services\Orders\OrderStateMachine` (T12) s'appuiera dessus plutôt que de redéfinir la table de transitions.

## 2026-10-06 — T17 — Back-office commandes, expéditions, clients, tableau de bord

- **Remboursement limité au virement pour l'instant** : PLAN §9/§14 attend qu'un remboursement appelle l'API Stripe pour les paiements carte. T14 (intégration Stripe) n'est pas encore livrée (la cliente doit encore créer son compte Stripe) — plutôt que d'inventer un faux appel API, `RefundOrderAction` **refuse explicitement** ce cas via `RefundNotAvailable` (message clair à l'admin, aucune donnée modifiée). Seul le remboursement d'un virement est opérationnel (transition + avoir généré via le listener T16 déjà existant). **À lever dès que T14 est livrée** : il suffira de faire appel à un futur `StripeRefundService` dans la branche `PaymentMethod::Stripe` de `RefundOrderAction`, sans toucher au reste de l'action ni à l'UI.
- **Actions de transition en classes `Actions/Orders/` dédiées** (`ShipOrderAction`, `RefundOrderAction`) plutôt qu'inline dans `OrderResource`, conformément à CLAUDE.md §5 (logique métier hors UI) — sauf les transitions triviales sans effet de bord propre (préparer, marquer livrée) qui appellent directement `OrderStateMachine::transition()` depuis la ressource : ajouter une classe d'action dédiée pour un simple appel sans logique additionnelle aurait été une sur-abstraction.
- **`OrderResource::infolist()`** (détail commande) **découvert comme première utilisation des Infolists Filament dans ce projet** : `RepeatableEntry` pour afficher lignes de commande et historique de statut directement depuis les relations Eloquent (`items`, `statusHistories`), sans construire de vue Blade sur mesure. Le lien vers la facture est juste un texte (numéro), **pas un lien de téléchargement direct** depuis cette page — pour l'avoir, l'admin passe par la ressource « Factures & avoirs » (T16) ; dupliquer le mécanisme de lien signé ici aurait été redondant.
- **`UserResource` (Clients) en lecture seule** (pas de création, pas d'édition) : les clients gèrent déjà leur propre compte via l'espace client (T18/Fortify) ; un formulaire BO d'édition directe créerait un deuxième chemin de modification des données de compte, source d'incohérences (ex. changement d'email sans re-vérification). Seule exception déjà existante et volontaire : le champ `deletion_requested_at`, surfacé en lecture seule (badge + filtre) pour que l'admin voie les demandes de suppression de compte (PLAN §13) — leur traitement reste manuel (pas d'action "Supprimer le compte" automatisée en V1, la suppression réelle d'un compte ayant des commandes facturées pose des questions de conservation légale, `À VALIDER` comptable/juriste, PLAN §27 point 14).
- **`AdminResource` : un admin ne peut pas se supprimer lui-même** (garde-fou applicatif dans l'action `DeleteAction::before()`, pas une contrainte BDD) — évite un verrouillage accidentel du back-office si un seul compte admin existe. Pas de 2FA (déjà décidé hors V1, voir la décision "Changement de périmètre" plus bas) : juste guard `admin` séparé + mot de passe ≥ 12 caractères, cohérent avec `MakeAdminCommand` (T00).
- **Tableau de bord : CA du mois basé sur `paid_at`, nombre de commandes du mois basé sur `created_at`** — deux dates différentes, délibérément : le CA doit refléter l'argent réellement encaissé ce mois-ci (une commande créée fin septembre mais payée en octobre compte dans le CA d'octobre), alors que le volume de commandes reflète l'activité commerciale (créées, indépendamment du paiement). Le CA **n'exclut pas** les commandes ensuite remboursées (`Refunded`) — limitation assumée pour un simple indicateur BO ; le chiffre exact avec avoirs déduits reste la responsabilité de l'export comptable CSV (T16), pas de ce widget.
- **Vue « Expéditions »** : simple page Filament avec table (`Filament\Tables\Concerns\InteractsWithTable`), pas une ressource — aucune action d'édition/suppression n'y a de sens, seulement une lecture triée + mise en évidence visuelle (badge coloré) des commandes du jour/en retard.
- **Non fait, volontairement hors scope strict de T17** : aucun compteur « virements en attente » spécifique sur une page séparée au-delà du widget (déjà couvert), pas de recherche globale multi-ressources (Filament n'en fournit pas nativement sans plugin supplémentaire, non installé ici — à évaluer si le besoin se confirme).

## 2026-10-06 — T16 (complément) — Ressource Factures & avoirs + export CSV comptable

- **Correctif de process** : ce complément de T16 a été commencé par erreur directement sur `develop` (oubli de créer la branche avant de coder, même type de glissement déjà documenté en T04). Corrigé **avant tout commit** (aucun commit n'avait encore été fait) en créant `feature/T16-invoices-bo` et en y déplaçant tout le travail en cours — donc aucun impact réel, mais noté ici par transparence (QUALITE.md §10, principe d'auto-revue).
- **`InvoiceResource` en lecture seule strict** : pas de création/édition (`canCreate() => false`, pas de page `edit`) — une facture émise est immuable (CLAUDE.md), donc le BO ne doit permettre que consultation + téléchargement, jamais une modification, même accidentelle via un formulaire Filament par défaut.
- **Téléchargement BO réutilise le mécanisme de lien signé existant** (`InvoiceDownloadController`, déjà utilisé pour l'accès invité) plutôt que de contourner la policy `InvoicePolicy` (qui ne fonctionnerait pas pour un admin : elle type-hint `User`, pas `Admin`, deux guards/modèles distincts). ## 2026-10-09 — Corrections de l'audit de sécurité
