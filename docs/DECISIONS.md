## 2026-10-05 — T00 — Base de données

- **MariaDB** utilisée aussi bien en développement qu'en test (pas de SQLite, même en test) : le projet repose sur des verrous transactionnels (`lockForUpdate`) et une numérotation séquentielle critique (factures, commandes) dont le comportement diffère entre moteurs SQL. Tester sur un moteur différent de la production aurait pu masquer de vrais bugs de concurrence. Alternative écartée : SQLite en mémoire (défaut Laravel), plus rapide mais jugé risqué ici.
- Deux bases locales créées manuellement (accès root MariaDB non disponible depuis les outils automatisés — nécessite un geste humain avec mot de passe) : `boulangerie_gluten` (dev) et `boulangerie_gluten_test` (tests), toutes deux accessibles par un utilisateur MariaDB dédié `boulangerie_gluten` (pas de compte `root` utilisé par l'application : moindre privilège).
- `phpunit.xml` ne surcharge que `DB_CONNECTION` et `DB_DATABASE` pour les tests ; hôte/identifiants restent lus depuis `.env` (jamais commités) pour ne jamais exposer de secret dans un fichier versionné.

## 2026-10-05 — T02 — Modèle de données

- **Table `users`** : la migration par défaut de Laravel (`name`) a été adaptée dans une **nouvelle** migration (`adjust_users_table_for_v1`) plutôt que modifiée directement, conformément à CLAUDE.md §3.4 (une migration déjà mergée dans `develop` ne se modifie jamais). Résultat : `first_name`/`last_name` séparés (PLAN.md §22), `phone` (obligatoire pour le SMS Chronopost, PLAN §9.1), `deletion_requested_at` (PLAN §13).
- **`orders.relay_snapshot`** stocké en JSON plutôt qu'en colonnes séparées (`relay_address_*`) : PLAN.md §9.4 identifie explicitement cette zone comme ambiguë ("quels champs exacts pour le snapshot complet ?"). Le JSON permet de capturer tout ce que l'API Chronopost renvoie (nom, adresse, horaires, distance) sans décider prématurément d'un schéma rigide ; `relay_id` et `relay_name` restent des colonnes dédiées (recherche/affichage rapides).
- **Pas de table `vat_rates`** : le modèle de données `PLAN.md §22` ne prévoit pas de table séparée pour les taux de TVA, seulement une colonne `products.vat_rate` (decimal). La "liste paramétrable" des taux sélectionnables en BO (mentionnée dans la fiche T02) relève de `spatie/laravel-settings`, installé en **T04** — non disponible en T02. Reporté à T04 : seeding réel des taux à ce moment-là (valeurs toujours **À CONFIRMER** par le comptable, CLAUDE.md §3.1).
- **Redirection générique `/products/{slug}` → `/produit/{slug}`** (PLAN §23) : non seedée dans `redirects` (table de correspondances exactes). C'est une règle de motif, implémentée dans le middleware de redirection (**T20**), pas une ligne de données.
- **`order_status_histories`** : table d'audit append-only, `UPDATED_AT` désactivé (`const UPDATED_AT = null`) — une ligne d'historique ne se modifie jamais.
- Les transitions de statut autorisées (PLAN §9.2) sont encodées directement sur l'enum `OrderStatus::allowedNextStatuses()` (donnée statique), pas dans un service séparé : `App\Services\Orders\OrderStateMachine` (T12) s'appuiera dessus plutôt que de redéfinir la table de transitions.

## 2026-10-06 — T15 — Paiement par virement

- **Resource Filament `OrderResource` créée mais volontairement réduite au strict besoin de T15** : liste (numéro, client, statut, paiement, total, date d'expédition), filtres statut/paiement + filtre bascule « Virements en attente », action « Valider le virement reçu ». **Pas de création/édition manuelle** (`canCreate() => false`, pas de page `edit` — le statut ne se modifie jamais autrement que via `OrderStateMachine`, CLAUDE.md §5), pas de recherche nom/email avancée, pas d'onglet Expéditions, pas de vue détail. **Tout cela relève de T17** (back-office commandes/expéditions/clients), qui devra **étendre** cette ressource plutôt que d'en recréer une — attention aux collisions de routes/noms si T17 régénère un `OrderResource` de zéro.
- **Pas de compteur « virements en attente » sur le tableau de bord** bien que PLAN §11 le mentionne : le fichier `tasks/T15-virement.md` (périmètre réellement scopé pour cette tâche) ne le liste pas dans son "À faire", contrairement au filtre BO qui lui y figure explicitement. Reporté à T17 (qui construit le tableau de bord commandes). Décision de suivre le découpage des fiches `tasks/` plutôt que PLAN.md quand les deux divergent sur le découpage (PLAN reste la référence fonctionnelle globale, `tasks/` fait autorité sur le périmètre exact de chaque tâche).
- **Date d'expédition recalculée à la validation du virement, pas à la relance/l'annulation** : un virement peut arriver plusieurs jours après la commande, donc la date initialement calculée par `CreateOrderAction` (au moment de la commande) est probablement obsolète. `ValidateBankTransferPaymentAction` la recalcule via `ShippingDateCalculator::forInstant(now())` **avant** de transitionner vers `Paid`, dans la même transaction verrouillée. Correctif Larastan nécessaire : ajout de `@property Carbon|null $planned_ship_date` sur `Order` (même piège déjà documenté en T12/T16 — l'écriture directe `$order->planned_ship_date = ...` n'est pas inférée correctement par Larastan sur un cast `'date'` sans cette annotation) + conversion explicite `Carbon::instance(...)` car `ShippingDateCalculator::forInstant()` renvoie une `CarbonImmutable`, incompatible avec le cast Eloquent `'date'` (qui attend un `Carbon` mutable).
- **Emails de virement envoyés via `Mail::queue()` directement**, sans passer par une Notification Laravel ni par un listener d'événement dédié : `BankTransferInstructionsMail` est envoyé depuis `CheckoutWizard::pay()` (symétrique au point où la redirection diffère déjà selon `payment_method`), `BankTransferPaidMail` depuis `ValidateBankTransferPaymentAction` (seul point qui connaît la nouvelle date d'expédition), `BankTransferReminderMail`/`BankTransferCancelledMail` depuis la commande planifiée. Pas de câblage Brevo réel à ce stade (`MAIL_MAILER=log` en dev) — le transport SMTP/API Brevo reste un sujet T19, mais les `Mailable` eux-mêmes sont déjà la version définitive (changer de transport ne nécessitera aucune modification de ces classes).
- **Relance "à mi-délai"** : calculée comme `cancel_after_days / 2` (ex. 2,5 jours pour un délai de 5 jours par défaut), pas un paramètre BO séparé — PLAN §11 ne demande pas de paramètre distinct pour ce seuil, juste "à mi-délai". Marquage anti-doublon via une nouvelle colonne `orders.bank_transfer_reminder_sent_at` (nouvelle migration, jamais d'ajout sur une migration déjà mergée — CLAUDE.md §3.4), volontairement **non fillable en masse** (même principe que `User::deletion_requested_at` en T18) : seule la commande planifiée doit pouvoir la renseigner.
- **Tâche planifiée horaire** (`orders:process-bank-transfer-deadlines`, `routes/console.php`) plutôt que journalière : une échéance de quelques jours mérite une résolution plus fine qu'un batch quotidien (évite qu'une annulation ou relance traîne jusqu'à 24h de plus que nécessaire). Nécessite que le scheduler Laravel (`php artisan schedule:run` en cron minute, déjà requis par `cart:purge-old-guests` depuis T08) tourne réellement en prod — point à vérifier en recette (T24)/déploiement (T25), déjà une dépendance connue du projet.
- **BO : action blindée contre les doubles conditions** (déjà payé/annulé, ou pas un virement) via une exception dédiée `BankTransferValidationNotAllowed`, jamais par une simple vérification silencieuse — un admin qui clique sur l'action sur la mauvaise commande reçoit un message d'erreur explicite (notification Filament), pas un échec silencieux.

## 2026-10-06 — T13 — Tunnel de commande

- **Étape "Relais" provisoire** (PLAN §8.1, §9.1) : T11 (sélecteur de relais Chronopost réel) reste bloquée par T01 (identifiants/documentation Chronopost jamais fournis). Au lieu de bloquer tout le tunnel de commande, l'étape 2 (`CheckoutWizard::goToStep`) demande une **saisie manuelle** du nom/ville du relais souhaité (champs `relay_name`/`relay_postal_code`), avec un avertissement visible côté client ("recherche en cours de finalisation, nous confirmerons par email"). `CreateOrderAction` reçoit `relay_id = 'MANUEL-'.timestamp()` et un `relay_snapshot` qui documente explicitement `'note' => 'Saisie manuelle provisoire (T11 non livrée)'`. **Aucun comportement de l'API Chronopost n'a été inventé** (CLAUDE.md §3.1) : ceci est un stub d'UI, pas une simulation d'API. **À remplacer entièrement dès que T11 est livrée** : il faudra alors (1) remplacer l'étape 2 par le vrai sélecteur de relais, (2) supprimer le `relay_id` factice, (3) repasser en revue toute commande déjà créée avec un `relay_id` commençant par `MANUEL-` pour confirmer/corriger le relais réel avant expédition (point métier à traiter en BO, pas de migration de données nécessaire).
- **Paiement Stripe (T14) non encore intégré** : la route `checkout.stripe.start` existe et `CreateOrderAction` s'exécute normalement (commande créée en `pending_payment`), mais elle affiche pour l'instant une page d'attente (`checkout/stripe-pending.blade.php`) plutôt que de rediriger vers une vraie session Stripe Checkout. **Ne jamais afficher un message de paiement accepté tant que le statut en base n'est pas réellement `paid`** — c'est respecté ici (voir aussi `checkout/confirmation.blade.php`, branche `@elseif ($order->status === OrderStatus::Paid)`). À remplacer en T14 par : création d'une session Stripe Checkout (`checkout.session.create`), redirection réelle, puis le contrôleur `stripeStart` devient inutile (le webhook T14 gère la suite via `OrderStateMachine::transition(..., OrderStatus::Paid)`).
- **Routes de commande liées au `token` de la commande, jamais à son `id`** (`Route::get('/commande/stripe/{order:token}', ...)`, idem `checkout.confirmation`) : évite toute énumération séquentielle des commandes (IDOR) sur ces pages publiques/non authentifiées. Confirmé par un test manuel que `route('checkout.stripe.start', $order)` génère bien une URL avec le token (liaison de clé de route Eloquent personnalisée, cf. doc Laravel sur `getRouteKeyName`/`{param:field}`).
- **Garde-fou double-clic sur "Payer"** : propriété `submitting` sur `CheckoutWizard`, mise à `true` **uniquement après** que la validation (`cgvAccepted`, `paymentMethod`) ait réussi (sinon elle resterait bloquée à `true` indéfiniment si la validation échoue — bug repéré et corrigé avant tout commit). Un second appel à `pay()` alors que `submitting` est déjà `true` est ignoré immédiatement (`if ($this->submitting) { return; }`). Testé en simulant deux appels `->call('pay')` successifs sur la même instance Livewire (`tests/Feature/Checkout/CheckoutWizardTest.php`).
- **Blocage "configuration de livraison incomplète"** (PLAN §8.4, réutilise la logique déjà posée en T08/T09/T10 via `CartService::totals()['shipping_error']`) : message client **neutre** (ne révèle aucun détail technique) + `Log::critical(...)` comme "alerte admin" (pas de notification BO/Brevo dédiée — aucune n'existe encore dans le projet ; `ShopSettings::admin_notification_email` existe comme champ mais n'est câblé à aucun envoi réel. À reprendre en T19 (Brevo) si une vraie alerte email est souhaitée).
- **Piège Blade découvert et corrigé** : la directive `@disabled($submitting)` placée directement dans les attributs d'un tag de composant (`<x-ui.button ... @disabled($submitting)>`) casse la compilation Blade du composant (le compilateur de tags de composants ne gère pas bien un directive conditionnelle à l'intérieur de ses propres attributs — génère un `<?php endif; ?>` orphelin). Retiré ; la protection anti-double-clic reste pleinement assurée côté serveur par `submitting`, et `wire:loading.attr="disabled"` suffit côté UX pour le bouton "Payer". **Piège à connaître** pour toute IA qui ajouterait `@disabled`/`@checked`/`@selected` sur un composant Blade (`<x-...>`) plutôt que sur un élément HTML natif.
- **Piège de validation Laravel découvert et corrigé** : la règle `regex:/^(0|\+33)[67][0-9]{8}$/` pour le téléphone contient un `|` littéral dans l'alternative `(0|\+33)`. Écrite en chaîne pipée (`'required|regex:/^(0|\+33).../'`), ce `|` est interprété à tort par Laravel comme un **séparateur de règles** et casse la regex (`preg_match(): No ending delimiter '/' found`), détecté uniquement à l'exécution des tests Livewire (jamais déclenché avant car ce champ n'était pas encore testé). Corrigé en passant la règle en **tableau** (`['required', 'regex:/^(0|\+33)[67][0-9]{8}$/']`) sur l'attribut `#[Validate]` et dans `goToStep()`. **Règle générale à appliquer partout ailleurs dans le projet** : toute regex de validation contenant un `|` doit être écrite en tableau de règles, jamais en chaîne pipée.
- **"Créer mon compte" après commande invité** (PLAN §13/§9.1) : lien simple vers `route('register', ['email' => $order->email])` sur la page de confirmation, sans logique de pré-remplissage complexe. `resources/views/auth/register.blade.php` (vue Fortify minimaliste de T03, jamais restylée) a été légèrement modifiée (une ligne) pour préremplir le champ email depuis `?email=` si présent — pas de refonte de cette vue (hors périmètre T13, toujours "à finaliser" selon la note de T03).
- **CGV / droit de rétractation** : texte affiché à l'étape Paiement cite l'article L221-28 du Code de la consommation (droit de rétractation non applicable aux denrées périssables/personnalisées) — fait juridique générique et public, pas une donnée métier propre à la cliente (ne viole pas CLAUDE.md §3.1). Le lien vers les CGV complètes pointe vers la page `content.show` de slug `cgv` (déjà seedée en T02/T20). **À faire valider par la cliente/son comptable avant mise en production réelle** (CHECKLIST-PROD.md).

## 2026-10-06 — T16 — Factures et avoirs PDF

- **Bug de schéma corrigé** : `invoices.total_ht/total_vat/total_ttc` créées en `unsignedInteger` en T02, avant que les avoirs (montants **négatifs**, PLAN §12) ne soient conçus. Migration séparée (`alter_invoices_totals_signed`) plutôt que de modifier la migration T02 déjà mergée (CLAUDE.md §3.4) — colonnes passées en `INT` signé via SQL brut (`DB::statement`), plus fiable que `->change()` (doctrine/dbal) sur MariaDB pour ce cas précis.
- **`SequenceGenerator`** extrait de `CreateOrderAction` (T12) en service partagé : factures (`type='invoice'`, préfixe `F`) et avoirs (`type='credit_note'`, préfixe `A`) réutilisent la même mécanique de verrouillage que les commandes.
- **`barryvdh/laravel-dompdf` ^3.1**. PDF stocké sur le disque `local` (privé par défaut en Laravel 11+, `storage/app/private`) — jamais sur le disque `public`.
- **Téléchargement** : `Gate::authorize('view', $invoice)` (policy : facture liée à une commande du client connecté) **sauf** si l'URL porte une signature valide (`hasValidSignature()`), auquel cas l'accès est autorisé sans authentification — pour le lien envoyé à un client invité (30 jours, à générer lors de l'envoi de l'email en T19).
- **Répartition HT/TVA par taux** : `vat_summary` dans le snapshot regroupe les lignes de commande par `vat_rate` — résout proprement le relevé approximatif (taux moyen pondéré) posé en T12 pour `orders.total_ht/total_vat`, qui reste une approximation sur la commande elle-même (non modifiée ici) mais est correctement détaillé par taux **sur la facture**, qui est le document qui compte réglementairement.
- **Listeners idempotents** : `GenerateInvoiceOnOrderPaid`/`GenerateCreditNoteOnOrderRefunded` vérifient l'absence de facture/avoir existant avant d'en émettre un nouveau — protège contre un événement rejoué (ex. webhook Stripe livré deux fois, T14).
- **Non fait, à prévoir séparément** : ressource Filament "Factures & avoirs" + export comptable CSV (PLAN §14) — reporté faute de temps, le cœur (génération, snapshot immuable, téléchargement sécurisé) était la priorité. Le montant/texte des mentions légales (raison sociale, SIRET, formats de numéros) reste `À VALIDER` par le comptable (CLAUDE.md §3.1) : le PDF affiche des placeholders explicites tant que `BillingSettings` n'est pas renseigné.

## 2026-10-06 — T12 — Commandes : création, statuts et transitions

- **Numérotation des commandes réutilise la table `invoice_sequences`** (déjà créée en T02, colonnes génériques `type`/`year`/`last_number`) avec `type = 'order'`, plutôt qu'une table dédiée identique. Incrément sous `lockForUpdate()` dans la même transaction que la création de la commande.
- **`OrderStateMachine::transition()`** : unique point d'écriture de `orders.status`, verrouillé (`lockForUpdate`), historise systématiquement, déclenche l'événement correspondant (`OrderPaid`/`OrderShipped`/`OrderCancelled`/`OrderRefunded`) une seule fois par transition. **Aucun listener branché pour l'instant** (facture, email) : ils arriveront avec T16/T19, qui se contenteront d'écouter ces événements déjà en place.
- **`CreateOrderAction`** ne fait confiance à aucune valeur externe pour les montants : tout vient de `CartService::totals()` (déjà validé en T08/T09/T10). Accepte relais/paiement en paramètres **génériques** (pas d'appel Chronopost/Stripe réel) : testable dès maintenant, bien que T11/T13/T14/T15 (qui fourniront ces paramètres depuis un vrai tunnel) restent bloquées par T01.
- **Larastan ne déduisait pas les types castés** (`OrderStatus`, `PaymentMethod`, `Carbon`) sur les écritures de propriétés (`$order->status = $to`), seulement les lectures — ajout d'annotations `@property` explicites sur `Order` pour corriger, plutôt qu'un baseline/ignore (jamais de suppression d'erreur sans corriger la cause, QUALITE.md).
- `total_ht`/`total_vat` calculés via un **taux de TVA moyen pondéré** des lignes (une seule TVA possible sur `orders`, alors que chaque produit a son propre taux) — approximation documentée, à affiner en T16 avec le détail par taux sur la facture (qui, elle, a un récapitulatif multi-taux).

## 2026-10-06 — T08 — Panier

- `CartService` (hors Livewire, QUALITE.md §4.2) consomme directement `ShippingCostCalculator`/`ShippingDateCalculator` (T09/T10) : pas de texte de repli "calculés à l'étape suivante" grâce au réordonnancement de tâches décidé en T10.

## 2026-10-06 — T05 — Catalogue back-office

- **`spatie/laravel-medialibrary` ^11.23** + **`filament/spatie-laravel-media-library-plugin` ^3.3**. Nécessite l'extension PHP `gd` (absente par défaut sur la machine de dev — installée en cours de tâche : `sudo apt-get install php8.3-gd`). Driver d'image : `gd` (config par défaut du package), conversions converties en **WebP**, **non queued** (`->nonQueued()`) : exécutées immédiatement à l'upload plutôt qu'en file d'attente — plus simple pour un back-office à faible volume (~70 produits), évite un état transitoire "image pas encore convertie" si le worker de queue n'est pas démarré.
- **Piège Larastan résolu** : sur un objet `Conversion`, `->nonQueued()` doit être appelé **avant** `->fit()`/`->format()` (ces méthodes de manipulation d'image proxient ensuite vers `Spatie\Image\Drivers\ImageDriver`, qui n'a plus la méthode `nonQueued()`). Documenté ici pour la prochaine IA qui ajouterait une conversion.
- **Texte alternatif par image (obligatoire pour publier, PLAN.md §6.2)** : le plugin Filament ne permet pas nativement un champ de formulaire par fichier individuel dans un upload multiple. Solution retenue : `SpatieMediaLibraryFileUpload` gère l'upload/réordonnancement, et un `Repeater` séparé (`galleryAltTexts`) — hydraté depuis les médias déjà attachés, sauvegardé via `afterSave()`/`afterCreate()` sur les pages Filament — gère le texte alternatif de chaque image. **Limite connue** : à la création, les images tout juste uploadées n'apparaissent dans ce Repeater qu'après un premier enregistrement (flux "uploader puis légender à l'édition"), ce qui est raisonnable en usage réel BO.
- **Taux de TVA** : proposé en `Select` avec les 4 taux légaux français (2,1 % / 5,5 % / 10 % / 20 %) plutôt qu'un champ libre — ce sont des paliers légaux publics, pas une valeur métier inventée ; le taux **applicable à chaque produit** reste à valider par le comptable (inchangé depuis T02/T04).
- **Suppression bloquée si le produit a été commandé** (`Product::hasBeenOrdered()`) : appliqué sur l'action de suppression individuelle, la suppression définitive (ForceDelete) et la suppression groupée — pas de contrainte FK en base (`order_items.product_id` en `nullOnDelete`), donc la règle est strictement applicative (Filament), pas un piège silencieux au niveau BDD.
- Tests medialibrary : disque `public` **toujours faké** (`Storage::fake('public')`) pour ne pas écrire de vrais fichiers sur disque pendant la suite de tests.
